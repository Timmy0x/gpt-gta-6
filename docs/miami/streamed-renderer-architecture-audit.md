A streamed photorealistic layer can be integrated with the game. It is a plausible way to improve geographic appearance quickly, but the current globe preview does not establish shared gameplay depth, physical support or correct datum alignment. The smallest production architecture I recommend keeps Babylon and the local simulation, with the streamed layer drawing through the same scene/depth pipeline. This is an engineering recommendation, not an implementation already proven in the game.

This audit inspected the exact isolated `3d-tiles-renderer` 0.5.2 installation against Babylon 9.25.0, the current upstream backend, and frozen Miami game R5. Version 0.5.2 is the latest official release (August 24); its Babylon peer range includes 9.25.0, though its development dependency remains 8.47.2. Source hashes and the CPU camera probe are recorded in `docs/evidence/miami-streamed-architecture-r1/inspection.json`. No application source, dependency, Git state or frozen build was changed. [Release](https://github.com/NASA-AMMOS/3DTilesRendererJS/releases/tag/v0.5.2), [package manifest](https://github.com/NASA-AMMOS/3DTilesRendererJS/blob/v0.5.2/package.json).

The backend explicitly supports right-handed scenes only. It accepts GLB/glTF/B3DM; its documented limitations include geographic-region bounds, I3DM/PNTS, conservative bounding boxes and limited caching. Exact 0.5.2 code confirms that unsupported region-only bounds cannot provide a valid visible volume. `checkCollisions` merely marks loaded Babylon meshes for the legacy collision coordinator; it does not create Havok bodies. Its byte-accounting method returns 1, so a nominal byte cap does not constrain actual geometry/texture allocation. These must be handled explicitly before a bounded game integration. [Backend guide](https://github.com/NASA-AMMOS/3DTilesRendererJS/blob/master/src/babylonjs/renderer/README.md), [backend implementation](https://github.com/NASA-AMMOS/3DTilesRendererJS/blob/master/src/babylonjs/renderer/tiles/TilesRenderer.js).

R5 creates a default left-handed Scene before loading assets and constructing Havok. Its player uses UniversalCamera, 0.12–1500 m clipping, changing scope FOV and a final DefaultRenderingPipeline. Camera movement, weapon rays and vehicle forward directions already use local X=east, Y=up, Z=north. Changing `scene.useRightHandedSystem` after boot is invalid as a migration: our installed Havok plugin captures handedness when constructed, and Babylon's GLTF importer changes root conversion and material orientation based on the scene. A fresh right-handed rebuild is possible, but would require revalidating every model axis, camera/weapon direction, winding, joint frame, vehicle seat, water/reflection and physical query. It is the broadest option.

For the minimum production route, adapt the Babylon backend to the existing left-handed scene using the shared renderer core, or use an upstream implementation once LH support is validated. The bounded adapter must preserve the GLTF loader's automatic conversion exactly once, compose the GLTF up-axis/tile-parent/georeference transforms consistently, transform bounding volumes and camera frusta in the same basis, and handle mirrored winding/normals. Merely applying a negative scale to `tiles.group` is not a demonstrated fix: the current helper overwrites its imported root quaternion before composing transforms. Validate this adapter first with independently licensed asymmetric GLBs and nested transforms, including a 1 m marker and four compass directions. [GLTF helper source](https://github.com/NASA-AMMOS/3DTilesRendererJS/blob/master/src/babylonjs/renderer/loaders/GLTFLoader.js).

The quickest intermediate integration proof could retain two Babylon scenes on ONE engine, drawing both into the SAME color/depth attachment: existing LH game plus RH tile scene, with the tile camera at `(x,y,-z)` and its target similarly reflected. My four-point CPU probe under Babylon 9.25.0 produced identical normalized screen coordinates and depth, maximum difference 0, for matched aspect/FOV/clip planes. That proves only camera mathematics. Render order must not clear the shared depth, and the postprocess pipeline must run once after both opaque passes. The current game pipeline cannot simply be left independently attached and assumed to preserve that depth. Water, shadows and picking also cross scene boundaries. A separate Cesium/Three canvas or ordinary transparent overlay has no common depth and will let foreground/background occlude incorrectly; synchronized cameras alone do not solve it. The one-scene adapter avoids that ongoing composition burden.

Keep the game camera, viewport and player controls. Update tile traversal after the interpolated game camera is final, use the actual render resolution, and pass the changing scope FOV. Keep compatible near/far projection and depth convention on both WebGPU and WebGL. The globe demo's GeospatialCamera and huge clipping range are appropriate to a globe viewer, not automatic replacements for our third-person camera. The library's official Babylon guide requires shared ES-module Babylon resolution to avoid two incompatible engine copies. [Babylon integration guide](https://github.com/BabylonJS/Documentation/blob/master/content/features/featuresDeepDive/geospatial/loading3dTiles.md).

Coordinate reconciliation needs a dedicated contract. 3D Tiles uses metres and right-handed coordinates, commonly WGS84 ECEF; geographic region heights are ellipsoidal. Apply GLTF node transforms, GLTF Y-up to tile Z-up and the full parent tile transform before the ECEF-to-local frame. Our current `projectMiami` instead calculates horizontal East/North from the ellipsoid at height zero and directly assigns NAVD88 to Y; it is not a full three-dimensional ECEF frame. Therefore a guessed constant Y shift is insufficient evidence of alignment. Preserve source frames and epochs, transform the independently sourced NAVD88 geometry into a common local frame, and validate known independent ground controls. GEOID18 specifically expects NAD83(2011), not arbitrary WGS84 heights; the horizontal/reference-frame conversion must accompany the vertical conversion. Use a documented transformation, not a guessed geoid offset. [3D Tiles coordinate/transform specification](https://github.com/CesiumGS/3d-tiles/blob/main/specification/README.adoc), [NOAA GEOID18 frame requirements](https://www.ngs.noaa.gov/GEOID/GEOID18/geoid18_tech_details.shtml).

Compose large ECEF translations in double precision before converting to small local rendering/physics coordinates. R5 does not enable high-precision matrices, so introducing million-metre values into ordinary Float32 matrices before subtracting the origin would lose detail irreversibly. Babylon has explicit high-precision/floating-origin facilities, but local Havok coordinates remain the least disruptive choice for this Brickell integration. City expansion would later need a tested origin/region migration across vehicles, constraints, character controllers, queries, saved positions and cameras. [Babylon large-world rendering](https://github.com/BabylonJS/Documentation/blob/master/content/features/featuresDeepDive/scene/large_world.md).

Preserve two independent readiness states: `visualReady` for usable tile coverage and `collisionReady` for our actual Havok support. R5 already pins collision preparation and resolves named travel only after loaded shape/ground checks. Keep that contract. Visibility/LOD changes must never remove the ground under a player, car or NPC, nor camera-facing selection remove physics behind the camera. Continue predicting collision coverage from position, speed and stopping distance; block/slow entry when support is unavailable. A failed Google request cannot turn a previously safe platform into empty space. The four unsourced bridge decks stay unavailable until an independently permitted physical source exists. Loading an image of them does not satisfy that gate.

For a source whose agreement permits gameplay collision, a technical extension can create ephemeral near-player static Havok triangle shapes from resident content, pin them independently of visual LOD, swap replacements only at a fixed physics boundary and release bodies before disposing their mesh buffers. Collision creation, mesh winding, thin surfaces, maximum cooking work and memory need tests; stream-level bounding boxes alone are not usable building collision. This paragraph describes a technical option, not permission to derive Google collision assets.

For Google, the initial architecture should treat the service as live visualization and keep physics derived from our separate permitted GIS/mesh sources. Google's policy restricts storage/extraction and non-visualization uses; keeping a derived mesh only in RAM does not itself establish permission for that use. It also allows independently sourced 3D overlays and requires visible Google Maps branding plus viewport-dependent data credits. Do not persist tile responses, derived geometry or indexes in our repository, IndexedDB, service-worker cache or exported map packages. Follow the applicable agreement and response caching headers. The audit does not claim that every proposed game use is authorized or prohibited. [Google Map Tiles policies](https://developers.google.com/maps/documentation/tile/policies).

The exact auth code has operational defects relevant to the preview: the first Google 3D fetch consumes JSON without preserving a failed HTTP status; failed token-refresh promises remain cached; the Cesium root plugin catches an error and can resolve undefined. Thus neither a resolved root promise nor an empty request queue is readiness. Listen for load errors, preserve sanitized HTTP status without logging credentials, validate root shape and actual visible coverage, and recreate failed auth state on explicit retry. Both Google and ion's external-Google path default to no logo. Render ALL returned credits and the official Google Maps attribution, not only `attributions[0]`. [Google auth source](https://github.com/NASA-AMMOS/3DTilesRendererJS/blob/v0.5.2/src/core/plugins/auth/GoogleCloudAuth.js), [Cesium auth plugin](https://github.com/NASA-AMMOS/3DTilesRendererJS/blob/v0.5.2/src/core/plugins/CesiumIonAuthPlugin.js), [Google renderer request/credit guidance](https://developers.google.com/maps/documentation/tile/create-renderer).

A concrete next checkpoint is one source-aligned Brickell block: one shared-depth player/car view, independent native collision, compass/1 m checks, scoped aiming, roof/street occlusion, tile LOD transitions, failed/auth-expired requests and all existing travel boundaries on both rendering backends. Enforce a tile-count cap until real buffer/texture accounting is implemented, then bound aggregate visual/physics memory and frame cooking work. Keep the existing image/volume fallback behind an explicit availability state. Photogrammetry appearance alone does not provide separate destructible trees, interiors, vehicle interaction, temporal lighting or NPC semantics; those remain our game systems and individually sourced assets. This checkpoint can prove a live streamed map integration without mislabeling a globe viewer as the finished game.
