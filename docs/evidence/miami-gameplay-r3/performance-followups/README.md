The first next optimization to investigate is the native point cache and cold camera query preparation. `CameraMeshQueries.entry()` calls Babylon `_generatePointsArray()`, which materializes one Vector3 object per native vertex before building its detached index bounds. In the retained-heap sample, 251004 vertices used 9.0MB of typed input, added 28.1MB of JS heap for native points, and 4.35MB for detached camera partitions. Native points cost 25.28ms to prepare; index bounds cost 28.28ms in that sample. Camera partitions are limited to 128 meshes/8192 parts and pruned when meshes become disabled/disposed; native Geometry points remain owned by the source geometry after visibility disable and after camera partition eviction. This does not prove a disposal leak: the fixture retains its mesh references through the observed stages. Raw source CPU buffers, native point arrays and Havok allocation are outside the current static GPU resource estimate. The renderer's 960/640 LRU count limit is a count safeguard; pinned backend byte estimate is 1, not a real resident byte budget.

`native-points-memory-observed.json` contains the observed values. `native-points-memory.ts` provides a focused reproduction with synthetic typed geometry; run with `node --expose-gc --import tsx .local-builds/miami-camera-performance-r3/native-points-memory.ts`. Its generated geometry differs slightly from the original floor-plus-far-triangle sample, so its numeric results should be labeled as a new workload if rerun. The source-point ownership behavior is the claim being reproduced. A future implementation could test direct typed-position native triangle math with scratch vectors, avoiding per-vertex point objects, or controlled preparation before a new visual LOD is first queried. Both require review of affine/instance transforms, two-sided hits, closest distance, exact endpoint triangle clearance, geometry mutation and synchronous visibility safety. No source-derived physical assets should be made. A single mesh exceeding 8192 parts would be evicted immediately by the existing bounded cache and rebuilt on subsequent queries; this is a potential oversized-input performance case, not a measured live tile case.

It must preserve framebuffer pixel error and common-frame source bounds. This is a synthetic method-level benchmark, not live traversal cost or browser FPS.

Population has identifiable allocation work but no measured total-update profile yet. `Population.update()` runs at every native 1/60s fixed step (`main.ts` lines 839–872). It constructs a new map of all road nodes at line284, filters/maps traffic people at line282, ranks nearby civilian drivers with repeated indexOf, sorts civilian distance ranking at lines374–377, and scans vehicles for every active driver/pedestrian. A stable road lookup with explicit road-graph revision invalidation is the smallest future change; production source roads are built at load, but native tests mutate the roads array, so constructor-only caching would be incorrect without an invalidation contract. Local budgets now constrain 30 residents and12 traffic vehicles; spatial driver/pedestrian queries should be justified by a measured workload before adding another index.

The fixed/render loop performs safety-critical support checks. `main.ts` lines997–1012 scans native dynamic bodies, bins anchors, adds enabled pedestrians/officers, submits active anchors, calls ensureCollision, updates residency and checks collisionReady every rendered frame. `MiamiResidency` demand maps/sorts 51 chunk records and checks 437 mesh records against primary/anchor distances; demand is also recomputed by queue release and stats reads. The public manifest describes 211968600 bytes of packaged input, not current resident memory. A future revision could cache demand per primary/anchor generation while retaining unconditional immediate native support checks, pinned/travel demand and retry events. Throttling all support work would risk cars/corpses falling through unloaded collision; no such change is recommended.
